## 用这些数字练「怎么说人话」

### 1. 异常% = 0.00%

意思：这两轮请求**都成功了**，没有压挂。  
入门第一关先过这个。

### 2. 商品列表一直很快（约 5ms）

读接口很轻，本机 5～10 人几乎感觉不到压力。  
平均值几乎没变 → 说明这个接口在当前压力下很稳。

### 3. 登录变慢了（255ms → 428ms）

登录比商品列表慢，而且人一多更明显。  
合理原因（面试可以这么说）：

- 登录要查库、校验密码（BCrypt 比较吃 CPU）
- 每个虚拟用户都在登录，登录本身就成瓶颈

所以：**不是「系统全挂了」，而是「登录接口更重」。**

### 4. 吞吐量为什么 10 人时数字看起来没变大？

别死盯一个数。本机、Ramp-Up、循环次数、是否开结果树，都会影响。  
入门结论先抓三点就够：

1. 有没有错（异常%）  
2. 谁慢（登录 vs 商品列表）  
3. 加压后谁变慢（登录变慢，列表几乎不变）

## 几个词对照（简历/面试用）

| 词 | 对应你报告里的 | 人话 |
|----|----------------|------|
| 并发用户 | 线程数 5 / 10 | 同时模拟多少人 |
| 响应时间 | 平均值、90%百分位 | 一次请求要多久 |
| 错误率 | 异常% | 失败占比 |
| 吞吐量 / TPS 近似 | 吞吐量（/sec） | 每秒完成多少次请求 |

> 严格说 TPS 常指「事务/秒」，JMeter「吞吐量」在入门阶段可以当成「每秒完成多少请求」来理解。

## 本课作业：写一段结论（可直接留存）

把下面模板填进你的学习笔记（或复制到 `jmeter/性能测试小结.md`）：

```text
【mall-admin-test 接口压测小结】

场景：登录 → 提取 Token → GET /api/products
工具：JMeter 5.6.3
环境：本机后端 8080 + MySQL

结果：
1. 5 线程与 10 线程下，异常率均为 0%
2. 商品列表平均响应时间约 5ms，加压后基本不变
3. 登录平均响应时间由约 255ms 升至约 428ms，说明登录接口更重（含密码校验）

结论：
当前小并发下读接口表现稳定；登录是相对瓶颈。
后续可单独对登录做阶梯压测，或优化 setUp 只登录一次再压读接口。
```

## 可选优化（知道即可，下节可做）

现在脚本是：**每个用户每次循环都登录**。  
更常见的压测写法：

```text
setUp：登录一次拿 token
 ↓
正式线程组：只用 token 压商品列表
```

这样测到的才更像「读接口的性能」，不会被登录拖累。  
第 4 课先会「读报告、写结论」；优化脚本可以下次做。
